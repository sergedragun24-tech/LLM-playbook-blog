# Канон: guardrails для LLM — проверенные источники, инструменты и границы надёжности

Собрано 13.08.2026 при проверке статьи по теме.
Проверять по этому файлу любую статью, где упоминаются guardrails, фильтрация промптов и ответов, промпт-инъекции, AI Firewall, DLP в ИИ-контуре.

## Термин: как писать

- При первом упоминании — связка **«guardrails (гардрейлы)»**, дальше только латиницей.
- «Гардрейлы» — калька второго уровня (словарь secpost.ru, explainllm.ru), поисковый спрос почти не формирует.
- Смежная формулировка, которая тянет вторую группу запросов: «фильтрация входных и выходных данных». Это язык ФСТЭК и ИБ-медиа.

## Каноны и фреймворки (проверено)

| Утверждение | Источник | Точная формулировка |
|---|---|---|
| Prompt Injection — риск №1 для LLM-приложений | [OWASP LLM01:2025](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) | «A Prompt Injection Vulnerability occurs when user prompts alter the LLM's behavior or output in unintended ways» |

| OWASP прямо рекомендует фильтрацию ввода и вывода | там же, LLM01 | «Implement input and output filtering… apply semantic filters and use string-checking to scan for non-allowed content» |
| NIST описывает и фильтрацию вывода, и её ограниченность | [NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf), Generative AI Profile, июль 2024 | «Many current systems restrict model outputs… but this approach may still produce harmful recommendations in response to other less-explicit, novel prompts» |

## Про «три слоя фильтрации» — как писать корректно

Схема «regex → NER → семантическая модель» **подтверждается по сути, но не является отраслевым стандартом с фиксированной нумерацией**:

- Конвейерность документирована дословно: NeMo применяет проверки «in the configured order»; Guardrails AI собирает несколько валидаторов в один Guard.
- Regex и NER у Presidio — **не два слоя конвейера, а два механизма одного детектора**. Подавать их как отдельные уровни — неточность.
- Модель-судья как отдельный уровень — да: Llama Guard, Azure Prompt Shields, self-check rails.

Рабочая формулировка: «guardrails собирают из нескольких независимых проверок — детерминированных (регулярные выражения, словари, контрольные суммы), статистических (NER-модели) и модели-судьи». Добавлять: «фиксированной нумерации слоёв в отрасли нет».

## Границы надёжности — обязательно для снятия оверклеймов

**«Guardrails исключают утечку» / «ловит независимо от того, вспомнил человек или нет» — оверклейм, писать нельзя.** Проверенные цифры:

| Цифра | Источник | Оговорка |
|---|---|---|
| Llama Guard 4 при фильтрации **вывода**: recall 69% (английский), 43% (мультиязычный); F1 61% и 51% | [карточка модели Meta](https://huggingface.co/meta-llama/Llama-Guard-4-12B) | Вендорские данные о своём продукте. Там же: модель «may be susceptible to adversarial attacks or prompt injection attacks» |
| Emoji smuggling — **100% успешных обходов** Azure Prompt Shield и Meta Prompt Guard; character injection в среднем 60–73%; алгоритмические AML-атаки 46–48% | [arXiv:2504.11168](https://arxiv.org/abs/2504.11168), принят на LLMSec 2025 | Препринт, но принят на воркшоп — помечать как препринт |
| Llama Prompt Guard 2: AUC .998, Recall @ 1% FPR — 97,5% | [карточка модели](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M) | Там же признаётся «Vulnerability to Adaptive Attacks» |
| Microsoft: Prompt Shields может пропустить атаку или отметить легитимный запрос, нужны дополнительные уровни проверки | [Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection) | Первичный, вендорский. Самая удобная цитата для снятия оверклейма |

Каноничная формулировка: **«guardrails снижают вероятность утечки на уровне архитектуры, к нулю её не сводят»**.

**Не использовать:** [arXiv:2511.22047](https://arxiv.org/html/2511.22047) («business-framed attacks 96.8%») — препринт одного автора без рецензии. Цифра красивая, источник слабый.

## Логическая ошибка, которую легко допустить

**«Тяжёлые семантические проверки выполнять параллельно с обращением к модели»** — для входного фильтра это неверно. Если запрос ушёл в модель одновременно с проверкой, данные уже покинули периметр, и фильтр опоздал. Параллельно допустимо считать только то, что не связано с утечкой: оценку качества ответа, детект джейлбрейка для статистики. Проверки на чувствительные данные идут **синхронно, до вызова модели**; ускоряют их каскадом (дешёвые правила на каждом запросе → модель-судья выборочно для категории повышенного риска).

## Русский PII: проверенный факт

Готовые распознаватели Presidio покрывают США, Великобританию, Испанию, Италию, Польшу, Сингапур, Австралию, Индию, Финляндию, Корею, Нигерию, Филиппины, Канаду, Швецию, ЮАР, Таиланд, Турцию, Германию. **Российских идентификаторов среди них нет** — ИНН, СНИЛС, серия и номер паспорта РФ, полис ОМС описываются отдельно. Проверено по [списку поддерживаемых сущностей](https://presidio.dataprivacystack.org/supported_entities/) 13.08.2026.
У ИНН и СНИЛС есть контрольные суммы, поэтому детерминированная проверка для них точна и дешева. Это и фактическая точность, и продающий аргумент в пользу российского провайдера.

## Российская нормативка — статус на 13.08.2026

- **Действует:** методический документ ФСТЭК от 12.04.2026 к приказу № 117 от 11.04.2025, п. **3.18 «Обеспечение защиты информации при использовании искусственного интеллекта»**. **Дословный текст пункта не подтверждён** — PDF на fstec.ru закрыт для автоматической выгрузки. Ссылаться только после ручной сверки.
- **Проект, не действует:** приказ ФСТЭК о защите ПДн (regulation.gov.ru, 24.07.2026, планируемое вступление 01.09.2026).
- **Проект, не действует:** ГОСТ Р «Разработка безопасного ПО, реализующего технологии ИИ» (ФСТЭК + ИСП РАН + Сбер), обсуждение до 17.09.2026. Содержит определение guardrails: «программы, обеспечивающие контроль и ограничение обработки входных данных и результатов работы модели по заданным правилам», и метрику «процент успешно отражённых атак типа prompt injection».
- Формулировка «требует закон» ни к одному из этих документов пока не применима.

## Разграничение терминов

| Класс решения | Где работает | Что перехватывает | Чего не закрывает |
|---|---|---|---|
| DLP | Периметр сети и агент на устройстве | Файлы, буфер обмена, исходящий трафик, обращения к запрещённым доменам | Смысл промпта, ответ модели, запросы с личного устройства |
| Guardrails | Внутри ИИ-приложения или шлюза | Текст промпта, текст ответа, смысл запроса | Любой трафик мимо этого приложения |
| AI Firewall, AI Secure Gateway | Отдельный сервис перед моделями | То же, что guardrails, плюс сетевые политики и лимиты по потребителям | Каналы, не заведённые на этот сервис |
| Корпоративный ИИ-шлюз (AI Gateway) | Единая точка доступа приложений к моделям | Аутентификацию, права, квоты, маршрутизацию, логи; guardrails встраиваются как проверка | Работу сотрудника в личном аккаунте |

## Тезисы, которые надо проговаривать (иначе скептик их снимет)

1. **Guardrails на шлюзе не закрывают теневой ИИ.** Нужен второй контур: блокировка доменов, allowlist, DLP на устройствах — плюс официальный канал, который удобнее личного аккаунта.
2. **Логи промптов сами становятся хранилищем ПДн и коммерческой тайны.** Режим доступа, срок хранения, размещение по 152-ФЗ.
3. **Маскирование обратимое или необратимое.** Необратимое затирание ломает задачу; обратимая токенизация требует словаря соответствий, который становится отдельным объектом защиты.
4. **Ложные срабатывания.** Юрист с номером договора, кадровик с ПДн, врач с диагнозом — фильтр срабатывает правильно, а работать мешает. Нужен процесс эскалации со сроком ответа, иначе сотрудник уходит в обход.
5. **Единая точка доступа — это и концентрация данных, и точка отказа.** Не педалировать «единый шлюз» как чистое благо.
